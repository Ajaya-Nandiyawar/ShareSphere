## Context

SRS Sec 3.4 defines two approaches for spatial operations (distance calculation and radius search):
- **PostGIS 3.3+**: Using `geography(Point, 4326)` columns and `ST_DistanceSphere` / `ST_DWithin` with GiST indexes.
- **Fallback**: Storing latitude/longitude as numeric columns and computing distance using a Haversine SQL expression.

The application relies heavily on spatial queries for matching (FR-MATCH-05) and browsing donations (FR-SRCH-04).

---

## Options

### Option A — PostGIS

| Criterion | Assessment |
|-----------|-----------|
| **Effort** | Low to write the SQL, but Medium to set up. Requires installing the PostGIS extension in the database cluster. |
| **Risk** | Low. PostGIS is the gold standard for geospatial data in PostgreSQL. GiST indexes ensure queries scale well as data grows. |
| **Performance** | High. Radius searches hit the GiST index directly instead of scanning the whole table. |
| **SRS constraints violated** | None identified. |

### Option B — Haversine Fallback

| Criterion | Assessment |
|-----------|-----------|
| **Effort** | Low to set up (no extension needed), but Medium to write. The SQL `ACOS(COS(RADIANS(...` formula is verbose and error-prone. |
| **Risk** | High at scale. Haversine distance calculations cannot use standard B-Tree indexes effectively, meaning a full table scan is required to find points within a radius. |
| **Performance** | Low. Poor scaling characteristics. |
| **SRS constraints violated** | None identified directly, but NFR-PERF-01 (if any) would suffer under load. |
